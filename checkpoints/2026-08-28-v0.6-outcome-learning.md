# Checkpoint — 2026-08-28 — v0.6 Outcome Learning

## Trigger

The private CRM contains heterogeneous outcomes that prove a binary accepted/rejected label is unsafe:

- accepted/completed historical Ticket2Europe mobility;
- first-place waitlist with BreGal;
- unranked waitlist with Youth BCN;
- rejection from a 430+ applicant pool with no individual feedback.

Treating these as equal training examples would corrupt selection heuristics.

## Design decision

Do **not** build an acceptance-probability model yet. Four outcomes do not support calibrated forecasting.

Instead, encode which learning updates are allowed from each outcome class and which causal inferences are forbidden.

## Implementation

`src/uexchanges/outcomes.py`

Canonical outcome classes:
- `ACCEPTED_COMPLETED`
- `ACCEPTED`
- `WAITLIST_PRIORITY`
- `WAITLIST_UNRANKED`
- `REJECTED_WITH_FEEDBACK`
- `REJECTED_HIGH_COMPETITION`
- `REJECTED_NO_REASON`
- `NO_RESPONSE`
- `WITHDRAWN`

Each record maps to a `LearningPolicy` containing selection signal, causal strength, permitted updates, near-accept state, forbidden inferences and explanation.

## Hard rules

1. Ranked priority waitlist ≠ ordinary rejection.
2. Waitlist rank 1–3 may create a weak positive/near-accept prior; never a negative application penalty without feedback.
3. An unranked waitlist remains near-accept/viable but must not invent rank, inherit a top-3 prior or create a negative penalty.
4. High-competition rejection without individual reason updates competition/base rate only.
5. No-response updates organisation response behaviour only; it is not a verified rejection.
6. Acceptance/completion supports a positive selection/relationship prior but does not prove every application component caused acceptance.
7. Only explicit organiser feedback can update call-specific negative criterion heuristics.
8. Specific feedback remains call/criterion scoped and never becomes a universal rule.
9. Historical application claims remain self-reported unless independently verified.

## QA learning during the wave

After PR #7 opened, Gmail outcome discovery found a real unranked waitlist (`Nature vs Psychology`, Youth BCN, 2023). The original schema only supported ranked waitlists.

The system did not coerce it into `WAITLIST_PRIORITY`. Instead v0.6 was amended before merge:
- new `WAITLIST_UNRANKED` type;
- rank forbidden for that type;
- weaker near-accept policy;
- schema/protocol updated;
- new regressions added;
- CRM `Outcome_History` + organisation graph updated.

This is the intended adversarial QA pattern: real data may expand the state machine; data must never be falsified to fit an enum.

## Tests added

10 outcome-learning regressions now cover:
- accepted/completed positive prior without component causality;
- rank-1 waitlist as near-accept, not negative;
- unranked waitlist as near-accept without positive top-rank prior;
- unranked waitlist rejecting an invented rank;
- 430+ high-competition rejection as base-rate-only evidence;
- explicit feedback enabling only specific heuristic learning;
- feedback outcome requiring actual feedback;
- no-response not being a rejection;
- ranked waitlist requiring rank;
- invalid waitlist rank rejected.
